# Add Debt

The Add tab contains a small native stack: AddHub → AddDebt, plus DebtOverview.
Utang and Kita are active (see [Income](income.md));
Essential Expense is disabled with a “Coming next” label. Home remains
the synthetic showcase. Done after saving pops back to the previous screen with a
fresh form on the next visit. View my debts opens/returns to the overview; see
[Utang Overview](debt-overview.md). Switching tabs retains the current form; Back discards an
unsaved form. Removal is blocked during saving so the owned operation can finish.

Presentation owns text state and calls one application operation per form session.
`parseDebtForm` maps friendly field errors and reconstructs exact domain inputs;
`createAddDebtOperation` supplies an ID, calls authoritative `Debt.create`, opens
an initialized database, saves through the existing DebtRepository, and closes
its connection. No schema, domain model, or repository changes are needed.

## Field semantics

- Debt name is required; provider is optional. Domain `nameText` constraints and
  normalization apply. Blank provider means absent.
- Balance is required and zero is valid. Balance and regular payment remain text
  until `Money.parse(text, 'PHP')`, followed by domain nonnegative validation.
  Ordinary ungrouped decimals accept up to two digits after the decimal point.
  Commas, currency symbols, exponents, excess precision, negatives and unsafe
  amounts fail. There is no floating-point currency arithmetic or rounding.
- Blank regular payment means absent; entered zero means known PHP zero.
- Interest requires an explicit unknown/known choice. Unknown carries no rate.
  Known accepts a nonnegative percentage with at most two decimal places.
  `parseInterestRate` concatenates whole/fraction digits into BigInt basis points,
  checks MAX_SAFE_INTEGER, then converts the checked integer to number. Thus
  1.25% is 125 basis points and 0% is known zero. Annual is the visible default
  period when known; Monthly is a separate choice. No accrual or conversion.
- Blank due date means absent. Entered dates must pass `FinancialDate.parse` as
  canonical YYYY-MM-DD calendar dates; no timestamps, clock or JS Date parsing.
- Recurrence is absent, monthly, or twice-monthly. Integer day text is validated
  through Recurrence factories, preserving anchors 1–31. Twice-monthly days must
  differ; the domain sorts them. No clamping or generated occurrences are stored.
- Payment, due date and recurrence remain independently optional.

## Identity, lifecycle and failures

The installed Expo SDK 57 stack already includes expo-modules-core 57.0.18.
Its exported `uuid.v4()` uses Expo's native UUID generator (Android's
`java.util.UUID.randomUUID`); no new package is installed. The application wraps
the generated string with `debtId`. IDs contain no financial/user information.
There is no timestamp/Math.random fallback if native generation is unavailable.

One ID is generated on the first valid submission and retained for that form's
retries. If SQLite commits and closing then fails, retry upserts the same ID
rather than creating another debt. IDs are neither generated by persistence nor
embedded in domain logic. This is in-memory retry identity, not a persisted draft
or cross-relaunch retry system.

Save disables controls and uses a synchronous ref guard against duplicate taps.
Success appears only after save AND close succeed, with a calm “Utang saved” state
and Done action. A failed save still closes the owned connection. If both fail,
AggregateError preserves both causes; close-only failure also propagates. Failed
opens are cleaned up by the existing database opener. UI errors never expose raw
exceptions, SQL or financial contents; all fields remain available for retry.
No financial values are logged, and no remote calls or analytics are added.

## Presentation and verification

The canonical board guided the cream background, restrained green primary surface,
small gold emphasis, serif headings, readable sans-serif fields and financial
numbers. Hub choices are stacked editorial rows, not a dashboard grid. The form
uses neutral surfaces and section dividers, with no decoration behind inputs.
The existing bottom bar, palette, system typography and safe-area ownership remain.

Fields have visible/accessibility labels, textual errors, scalable type and at
least 48-point practical targets. Radio choices expose checked/disabled state.
Saving and failure messages are live regions. A ScrollView inside a native
KeyboardAvoidingView keeps the form/save reachable without fixed keyboard padding;
the tab bar owns the bottom safe area. Return dismisses the keyboard, and tapping
Save works with it open. Device keyboard/large-text behavior still needs review.

Tests cover parsing boundaries, independent optional fields, IDs, domain
construction, cleanup/failure semantics, retry identity, hub/navigation, disabled
states, form errors, duplicate submission and delayed success. A real file-backed
host SQLite integration test saves via the application, closes/reopens and verifies
the complete entity, including recovery after a simulated post-commit close failure.
Host SQLite and Android export do not prove the native bridge or device appearance.

Device checklist for DK: open Add → Debt → enter synthetic debt → Save → verify
success → fully close app → relaunch → confirm normal initialization. Also review
keyboard reachability, large text, TalkBack and canonical visual balance. No debug
financial screen is included. Saved-debt reopen verification on native remains
pending physical execution. Task #013's overview now enables visual verification
after a full app restart; Home remains synthetic.
Visual review here is against the source layout/tokens, not product-owner approval
or a rendered physical-device comparison.

Not implemented: other entry types, debt edit/delete UI, real Home data,
Timeline, projections, financial strategies, sync, integrations or notifications.
